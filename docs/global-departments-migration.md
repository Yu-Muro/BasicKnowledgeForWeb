# 部署共通化の移行手順

## 変更内容
- 同じ名称の会期別部署を代表IDへ統合し、全会期で同じ部署を使う。
- 部屋割りの前日・当日担当とタイムテーブルの部署タグの参照を保持する。
- 既存一般ユーザーに所属を自動推定・仮割当しない。管理者が実際の所属を指定する。
- 管理者を除き、新規登録・一般ユーザーへのロール変更で所属部署を必須にする。

## 適用と運用

1. デプロイワークフローがHyperdriveのクエリキャッシュを無効化する。認証・所属・管理操作には最新のDB状態が必要なため、共通bindingのキャッシュを無効化し、接続プールは継続利用する。`CLOUDFLARE_API_TOKEN` には対象アカウントのHyperdrive編集権限が必要。失敗時は新版を公開しない。
2. `db:migrate:expand` で互換拡張を適用する。会期列・既存部署IDを保持し、所属列の追加、会期列のNULL許可、部署参照の単一FK化だけを行う。旧版の会期別検索・作成と部屋・予定の参照は継続できる。
3. 新版バックエンドを公開する。公開に失敗した場合、部署統合と会期列削除は実行しない。旧版は拡張済みDBで稼働を継続できる。
4. フロントエンドを公開する。新版は統合前の部署一覧を読み取れる。同名部署が一時的に複数表示される場合がある。
5. 両アプリの公開成功後、独立した `finalize-migrations` ジョブで `db:migrate` を実行し、同名部署を統合して会期列を削除する。統合が失敗しても、新フロントエンドと新バックエンドは公開済みのままとなる。
6. 新バックエンドは会期列が残っている間、部署・ユーザー所属・部屋・予定の変更とユーザー登録を `503` と `Retry-After: 30` で一時的に停止する。閲覧・ログインは継続できる。統合が完了し会期列がなくなれば書き込みを再開する。これにより統合マップの作成後に新たな参照・同名部署が追加される競合を防ぐ。
7. 管理者がダッシュボードのユーザー管理を開き、「所属未設定」の一般ユーザーの部署を指定して保存する。所属設定後、対象ユーザーはログインできる。

本番・開発とも同じ順序を使う。稼働中環境で公開前に通常の `db:migrate` を手動実行しない。新規の検証用DBでは全マイグレーションを一括適用できる。

### 移行失敗時の再実行

- 原因を解消後、同じデプロイワークフローを再実行する。適用済みのマイグレーションは履歴からスキップされる。
- `finalize-migrations` だけ失敗した場合は、そのジョブを再実行できる。両アプリは新版で稼働し、部署に関係する書き込みは移行完了まで停止する。
- DDLが部分適用され履歴が記録されていない場合も、削除・列追加は存在チェック付きとし、FKは既存制約を削除して再作成する。統合マップが残っている場合は現在の部署から再構築する。
- 会期列の削除は統合の最後に行う。列が残っている間は書き込み停止を維持し、失敗を無視して手動で列だけを削除しない。

部署名は文字列が完全一致するものを統合する。表記ゆれは管理者が確認する。既存ユーザーの所属を指定する前はログインを制限するため、適用直後に管理者が割当作業を行う。

`users.department_id` は管理者の所属免除と移行中の未設定ユーザーのため nullable とする。未設定の一般ユーザーを新規作成・一般ユーザーへロール変更するAPIは拒否し、未設定ユーザーのログイン・既存のユーザー認証セッションも拒否する。部署を本人が変更するAPIは提供しない。

ユーザー削除は論理削除であり、削除時に所属部署を解除する。メールアドレスの再利用はしない。管理者はダッシュボードの削除済み一覧から、部署を指定して復元できる。復元時にセッション世代を加算するため、削除前のログイン状態は復活せず再ログインが必要。発行済み `auth_token` もDB照合で拒否する。会期の `access_token` は従来の会期閲覧方式を維持する。

復元用の `session_version` 列は互換拡張で公開前に追加する。後続の `20261007121408_faulty_lady_mastermind` は同じ列を `IF NOT EXISTS` 付きで追加し、最終スキーマのスナップショットと移行履歴を記録する。互換拡張と統合の間でも新バックエンドのログイン・認証は稼働できる。

## 検証
`bun run db:test:departments` は一時DBを作成し、旧スキーマからの段階移行と再適用を検証してから削除する。PRのDB検証ジョブでも実行する。

一時CockroachDBで旧マイグレーションを適用後、複数会期の同名部署、部屋の担当、同一予定の重複部署タグ、既存ユーザーを作成して新マイグレーションを適用した。部署の1件への統合、部屋参照の維持、重複タグの1件への統合、ユーザー所属の指定、参照中部署の削除拒否、同名部署の重複拒否、マイグレーション再実行を確認した。

認証ではパスの除外一覧を使わず、`authMiddleware` が `ValidateSessionUseCase` に現在のユーザー状態の判定を委ねる。会期閲覧は `contentAccessMiddleware` の会期トークン経路を先に判定するため、古いユーザーCookieやHEADリクエストに影響されない。Server Componentの認証取得はReactのリクエスト単位の `cache()` で共有し、別リクエストへ持ち越さない。

キャッシュ方針は [Cloudflareの公式資料](https://developers.cloudflare.com/hyperdrive/concepts/query-caching/) に基づく。確認時点ではdevで有効、prodで無効だったため、公開ワークフローで両環境の無効化を保証する。
