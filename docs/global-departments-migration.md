# 部署共通化の移行手順

## 変更内容
- 同じ名称の会期別部署を代表IDへ統合し、全会期で同じ部署を使う。
- 部屋割りの前日・当日担当とタイムテーブルの部署タグの参照を保持する。
- 既存一般ユーザーに所属を自動推定・仮割当しない。管理者が実際の所属を指定する。
- 管理者を除き、新規登録・一般ユーザーへのロール変更で所属部署を必須にする。

## 適用と運用
1. デプロイワークフローが `db:migrate:expand` で互換拡張を適用する。会期列・既存部署IDを保持し、所属列の追加、会期列のNULL許可、部署参照の単一FK化だけを行う。旧版の一覧取得・会期別の部署作成・部屋と予定の参照は継続できる。
2. 新版バックエンドを公開する。公開に失敗した場合、部署統合と会期列削除は実行しない。旧版は拡張済みDBで継続稼働できる。
3. 公開成功後に `db:migrate` で同名部署の統合と会期列削除を行う。移行途中に設定されたユーザー所属も代表IDへ付け替える。新版は旧会期列を参照しないため、統合前後で読み書きできる。統合前は同名部署が複数表示される場合がある。
4. 統合が成功した後、フロントエンドを公開する。統合が失敗した場合はフロントエンド公開を止め、原因を解消して同じワークフローを再実行する。統合SQLはDrizzleのトランザクションで実行する。
5. 本番・開発とも同じ順序を使う。稼働中環境で公開前に通常の `db:migrate` を手動実行しない。新規の検証用DBでは全マイグレーションを一括適用できる。
6. 管理者がダッシュボードのユーザー管理を開く。
7. 「所属未設定」の一般ユーザーそれぞれの部署を選択し、「部署を保存」を押す。
8. 所属設定後、対象ユーザーはログインできる。

部署名は文字列が完全一致するものを統合する。表記ゆれは管理者が確認する。既存ユーザーの所属を指定する前はログインを制限するため、適用直後に管理者が割当作業を行う。

`users.department_id` は管理者の所属免除と移行中の未設定ユーザーのため nullable とする。未設定の一般ユーザーを新規作成・一般ユーザーへロール変更するAPIは拒否し、未設定ユーザーのログイン・既存のユーザー認証セッションも拒否する。部署を本人が変更するAPIは提供しない。

ユーザー削除は論理削除であり、メールアドレスの再利用はしない。発行済み `auth_token` もDB照合で拒否する。会期の `access_token` は従来の会期閲覧方式を維持する。

## 検証
`bun run db:test:departments` は一時DBを作成し、旧スキーマからの段階移行と再適用を検証してから削除する。PRのDB検証ジョブでも実行する。

一時CockroachDBで旧マイグレーションを適用後、複数会期の同名部署、部屋の担当、同一予定の重複部署タグ、既存ユーザーを作成して新マイグレーションを適用した。部署の1件への統合、部屋参照の維持、重複タグの1件への統合、ユーザー所属の指定、参照中部署の削除拒否、同名部署の重複拒否、マイグレーション再実行を確認した。
